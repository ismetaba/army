# T22 — Trigger workflows + live logs from the dashboard

Depends on: T18–T21. Read first: `tasks/SPEC.md` (CLI commands, Storage).
Goal: start, watch, and cancel runs without leaving the panel.

## Steps

1. `dashboard/src/lib/runner.ts` (server-only, module-level state):
   - `startRun(ws, kind, args: Record<string,string>)`: build the argv for
     `npx tsx <repoRootOfThisToolkit>/src/cli.ts <kind> …` (toolkit root = resolve from
     `process.cwd()/..`), spawn with `cwd` = workspace repoRoot, env passthrough;
     pipe stdout+stderr to `<awHome>/<ws>/pending/<pid>.log` until the CLI prints
     `run saved: <ws>/<runId>` — then move/append the log into that run's `log.txt`.
     Track `{ pid, ws, runId?, startedAt }` in a module map AND `<awHome>/<ws>/pending/pids.json`.
   - `cancelRun(pid)`: `process.kill(pid, 'SIGTERM')`; after 10 s escalate SIGKILL; the CLI's
     finally-block (T16) marks the manifest `cancelled` — add a SIGTERM handler in
     `src/cli.ts` that sets `status: 'cancelled'` before exit.
2. API:
   - `POST /api/trigger { ws, kind, args }` → `{ pid }`. Validate kind ∈ 3 workflows; args
     whitelist per kind (review: base/provider/model; test-feature: desc/url/allowDestructive/…;
     design-loop: feature/iterate/…). Reject anything else (no shell injection surface —
     always spawn with an argv ARRAY, never a shell string).
   - `GET /api/logs?ws=&pid=|run=` → SSE (`text/event-stream`): send existing content, then
     `fs.watch`-based tail; heartbeat every 15 s; close on client disconnect.
   - `POST /api/cancel { pid }`.
3. UI:
   - "New run" button on workspace page → modal: kind select + the per-kind arg fields
     (feature textarea, base input, url input, provider/model overrides) → trigger → jump to
     a live view streaming the SSE log (auto-scroll with pause-on-manual-scroll), Cancel
     button, and on completion a link to the finished run page.
   - T20's queued feedback gets an "Apply now" button: triggers
     `design-loop --iterate "<queued text>"` and removes it from the queue on success.
   - Running runs show a spinner badge in all run tables (poll `/api/runs` every 5 s or
     revalidate).
4. Concurrency guard: max 1 running workflow per workspace (409 with message otherwise).

## Acceptance

1. Trigger a review from the modal → live log streams tokens/tool calls → on finish the run
   appears with correct status and its Review tab renders.
2. Cancel mid-run → process exits, manifest `status: "cancelled"`, UI badge gray.
3. Apply a queued T20 feedback → an `--iterate` design-loop run starts and the queue entry
   disappears after success.
4. Second trigger on the same workspace while one runs → clear 409 message in the modal.
5. `args` containing `"; rm -rf ~"` executes nothing (argv array — verify the string arrives
   as a literal argument in the log).

## Out of scope
No auth (localhost-only tool), no multi-user, no queueing beyond the 1-per-workspace guard.

## Deviations

1. **`src/cli.ts` was NOT changed, and that is the finding rather than an omission.** Step 1 asks
   for a SIGTERM handler there that sets `status: 'cancelled'`. `src/store.ts` (T16) already
   installs one — `installGuards()` registers SIGINT/SIGTERM/SIGHUP, calls
   `finalizeOpen('cancelled', 'received SIGTERM')`, and exits 128+signal so the `process.on('exit')`
   handlers that stop dev servers still run. A second handler in `cli.ts` would be a second
   `process.exit()` racing the first. The window people worry about — a manifest written as
   `running` before the handler exists — does not exist either: in `startRun`, `writeManifest` and
   `installGuards()` are in the same synchronous block, and Node delivers a signal between event
   loop turns, never inside one. Verified rather than argued: cancelling mid-model-call gives
   `code=143` and a `cancelled` manifest (25/25 above), and cancelling *before* `startRun` runs
   leaves no manifest at all, which is correct.

2. **The transcript is filed as `<runDir>/spawn.log`, not appended to `log.txt`.** Step 1 says to
   move it into `log.txt`; doing so would duplicate almost every line, because `setLogSink`
   (src/workflows/common.ts) already mirrors every `log()` and every stdout line into `log.txt` as
   the run happens. What the transcript has that `log.txt` cannot is the argv header, `tsx` output,
   an uncaught stack, and everything printed BEFORE the run directory existed — worth keeping, and
   worth keeping separate. A run that never announces a run id keeps its transcript in `pending/`,
   where it is the only record of why; `sweepPending` collects those after 7 days.

3. **The interpreter is the toolkit's own `node_modules/.bin/tsx`, with `npx` as the fallback.**
   The canonical invocation is `npx tsx src/cli.ts` (SPEC § Fixed decisions) and that is what the
   panel SHOWS — but `npx` resolves `tsx` against the CHILD's working directory, which is the
   TARGET repo, and a target repo has no reason to depend on tsx. `npx` would then download it.
   The local binary is the exact thing `npx tsx` finds when run from the toolkit root, and it is
   one process instead of three — three more things to signal on cancel. The transcript prints the
   real `spawnargs`, so nothing is hidden.

4. **`--config` is in no allowlist.** It names a filesystem path, and a path chosen by a browser
   request is what SPEC § Dashboard security invariants #2 exists to prevent. `--workspace` is
   appended by the server from the validated registry entry, and has no field either.

5. **The panel works out a run's id while it is still running.** The CLI announces `run saved:
   <ws>/<runId>` only at the END (src/store.ts), so a four-minute run had no id to link to — and,
   worse, its `running` manifest looked like a run started in a terminal, so the banner listed the
   same run twice ("In progress (2)"). `adoptRunId` correlates the process with the one `running`
   manifest of the same kind in the same workspace created at/after the spawn, and only when there
   is exactly one unclaimed candidate; `run saved:` overrides it when it arrives. Found by looking
   at a screenshot, not by an assertion.

6. **The live view keys its stream on the pid, not on the run id.** The first version's effect
   depended on `initialRunId`; when a run finished, `router.refresh()` changed that prop from
   `null` to the id, the effect re-ran, and a second `EventSource` replayed the whole log on top of
   the first — the finished page showed everything twice. The stream key is now `pid=<n>` (stable
   for the page's whole life), the accumulated text lives in a ref that the effect resets, and
   `phase` is seeded from what the server already knows so a finished run never flashes "Running".
   Also found in a screenshot.

7. **`GET /api/runs` returns two lists and a resource count.** `runs` (manifests on disk) and
   `active` (children of THIS panel process) answer different questions and can legitimately
   disagree — a run started from a terminal is only in the first, and a run that has not written
   its manifest yet is only in the second. `stream` reports the watchers and timers `/api/logs`
   currently holds, which is what makes "a disconnect leaks nothing" a number someone can check
   instead of a claim.

8. **`/api/logs` does not use T21's `guardMutation`.** `EventSource` cannot set headers, so it
   could not. It does not need to: a cross-origin `EventSource`/`fetch` is subject to CORS and this
   route sends no `Access-Control-Allow-Origin`, so the browser refuses to hand the body to the
   page that asked. An `Origin`, when present, is still checked.

9. **`DELETE /api/feedback` matches on CONTENT, never on an index.** T20's queue is a file two
   tabs and a CLI can all append to; between the render that showed item 3 and the request to
   delete item 3, item 3 may be a different note. It removes exactly one occurrence of a
   `{text, createdAt}` pair, or reports the queue unchanged. It shares T20's per-directory
   serialisation, so an overlapping append and delete cannot lose each other's work.

10. **"Apply now" retires the item when the run STARTS, not when it finishes.** By then the
    feedback is in the child's argv and the workflow records it in `design.feedbackHistory`.
    Retiring it first would lose the note when the run cannot start (a busy workspace is a 409, and
    the commonest outcome); never retiring it would leave a button that starts the same run again
    on every click.

11. **Only pids in the runner's in-memory map can be signalled, and only this process's children.**
    `pending/pids.json` records `ownerPid` and is written for the human and the next process; it is
    never read back as authority. A pid from an earlier `next dev` may have been recycled by
    something unrelated, and "kill whatever holds pid 4711 now" is not something this module will
    do. The 1-per-workspace guard is therefore also in-memory: a run left over from a previous
    panel process does not block a new one.

12. **Runner state lives on `globalThis`.** `next dev` re-evaluates a module when it or one of its
    imports changes, and a re-evaluated module map would forget a running child — losing its log,
    its Cancel button and the guard while the process kept going.

13. **`dashboard/src/lib/trigger-args.ts` is a separate module from `runner.ts`.** The task names
    only `runner.ts`, but the allowlist has to be shared with the route (validation) and with the
    client modal (one field per entry, and the same error before a round trip), and `runner.ts`
    imports `node:child_process`. Same split, and same reason, as T20's `design-data.ts`.

14. **A `line`-kind field refuses line breaks; a `text` field allows `\n` and `\t`.** A git ref, a
    URL and a model id are one line by nature. The free-text positionals are what a textarea
    produces, so CRLF is normalised rather than rejected — but every other C0 control character is
    refused in both, for T20's reason: an ESC in a string the panel echoes into a copyable command
    is an ANSI sequence a terminal acts on, which quoting does not address.

15. **Screenshots are taken with `animations: 'disabled'`.** The first pass photographed
    `transition-colors` mid-interpolation and appeared to show the previously-selected workflow pill
    still highlighted. The computed styles were correct once settled; the assertion now checks the
    settled state and the capture finishes the transition first.

16. **Not done, deliberately:** no queue beyond the 1-per-workspace guard (out of scope), no
    trigger button on the home page (it spans workspaces; the run has to name one), and no "New
    run" for a workspace the registry has forgotten — the child's cwd comes from `workspaces.json`,
    so there would be no repo to run in.

17. **`GET /api/logs` primes a new stream with the last 256 kB, not the whole file.** Step 2 says
    "send existing content"; a design-loop `log.txt` is routinely megabytes, and the panel is a
    tail rather than an archive. The trim is announced to the reader as
    `…[earlier output trimmed: N bytes]`, and the run page's Log tab and `<runDir>/spawn.log` both
    still hold the whole thing.

## Corrections (2026-08-22, review follow-up)

- **The `run saved:` marker was missed whenever a chunk boundary landed mid-line before it.**
  `attachLog` funnelled both pipes into one scan buffer and matched `/^run saved: …/m`, so a
  stdout chunk ending without a newline put the marker somewhere other than a line start.
  Re-measured after the fix with an 86 KB model reply: the marker sits 66 072 bytes into the
  merged transcript and NOT at a line start — and the run id was still learned, `pending/` holds
  only `pids.json`, `spawn.log` is filed in the run directory and the live view links the run.
  The fix is a separate stderr tail (the marker is a single `writeSync(2, …)`) plus a widened
  `(?:^|\n)` anchor; `matchRunSaved` is exported and unit-tested in `runner.test.ts`.

- **The marker is corroborated before it is believed.** It is read out of the child's own stderr,
  and `log()` writes model output there verbatim — so a model reading a hostile repo could print
  `run saved: fixture/<someone-else's-run>` and re-point the panel at it, taking that run's
  `spawn.log` with it. `announcementIsOurs` now requires an unclaimed id whose manifest exists,
  is of the kind we started and is stamped at or after this child was spawned, and
  `archiveTranscript` refuses to write over an existing `spawn.log`. `adoptRunId` gained the
  `status === "running"` filter its own doc comment had always claimed.

- **Deviation 11's in-memory guard is no longer the whole guard.** A `detached` child survives
  `next dev` restarting, after which a second `design-loop` could be started into the same repo —
  two agents in one checkout, racing for ports 3001 and 5173. `orphanRunningIn` now also reads
  `pending/pids.json` for an entry owned by another panel process, and answers 409 only when that
  pid is alive AND its `ps` command line is still `…/src/cli.ts … --workspace <ws>` — which is what
  keeps the pid-recycling trap deviation 11 worried about closed. A run started in a TERMINAL is
  still deliberately not covered: nothing records its pid, and refusing on a stale `running`
  manifest alone would deadlock the panel.

- **`/api/logs` cannot be made to read an arbitrary file.** `runLogFile` joined `log.txt` onto the
  UNRESOLVED run directory, so `ln -s /etc/passwd <runDir>/log.txt` — which the designer/tester
  `bash` tool is free to create — streamed the target; `readLogTail` (T17) had the same gap, so the
  Log tab rendered it too. Both now go through a new `resolveRunFile` in `store.ts`, which
  `realpath`s the FILE and re-checks containment the way `resolveArtifact`'s gate 4 does, and
  `pump()` `lstat`s and opens with `O_NOFOLLOW` so the `pending/<pid>.log` transcript — which has
  no run directory to be contained by — is covered too.

- **The pending transcript is opened fresh, never appended to.** `flags: "a"` plus a 7-day sweep
  meant a recycled pid replayed a stranger's log; it is now `unlink` + `wx`, which also refuses a
  symlink re-planted in the gap.

- **`/api/feedback` uses the shared `guardMutation`** (see T20's corrections) — it was the one
  mutating route with no `Sec-Fetch-Site` check and the only one answering `{ok:false,error}`.

- **`Host` is pinned to loopback on every route, read and write** (see T21's corrections). Before
  the fix, a rebound page could `POST /api/trigger` and get a real child process, then stream the
  resulting `log.txt` back out of `/api/logs`.

- **Client components import their types instead of re-declaring them.** `run-poller.tsx` now
  imports `ActiveRun` from `runner.ts` and slices `RunManifest`; `live-log.tsx` uses `isRunStatus`
  from `trigger-args.ts`, where `RUN_STATUSES` is `satisfies readonly RunManifest["status"][]` — so
  a fifth status added to `shared/schemas.ts` fails the build instead of rendering as `done`.

- **`__proto__` in a config patch is a 400.** `z.strictObject` never sees that key, so it used to
  be silently dropped with a 200 while every other unknown key was rejected — a contract that was
  true except in one case. `prototypeKeys` scans the raw body before zod rebuilds it.
