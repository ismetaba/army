# T14 — Wire to the real project + handoff acceptance checks

Depends on: T13 (and all before it). Read first: `docs/HANDOFF.md` § Acceptance check.
Goal: prove the whole toolkit end-to-end on the developer's chosen repo.

## Steps

1. ASK the developer which repo to wire (do not guess). Run `aw init` against it
   interactively with them (fill real start commands/ports/test account env).
2. If the target has no frontend yet: ask which framework they want, scaffold it inside the
   first design-loop run (HANDOFF Step 0 note), keeping it minimal.
3. Run the acceptance sequence from HANDOFF, in order, in the target repo on a fresh branch
   `aw-acceptance`:
   1. `npx tsx <this-repo>/src/cli.ts design-loop "add a simple placeholder page" --config ./aw.config.json`
      → must produce screenshots + summary, stop for feedback.
   2. Re-run with `--iterate "make the heading bigger"` → must revise, re-screenshot, re-present.
   3. `npx tsx <this-repo>/src/cli.ts test-feature "the health endpoint returns 200 with build info"`
      (or the closest real endpoint) → must produce a report file.
   4. Review: the documented headless command from T12 (native or fallback) on the branch →
      verdict + severity-sorted findings.
4. Show the developer the final tree of every file created/modified in BOTH repos
   (`git status --short` + `find .claude screenshots test-reports -type f` in the target).
5. Fix anything that failed and re-run only the failed step, until all four pass.

viewports), a second iteration commit, a `test-reports/*.md` file, and a review verdict —
all shown to the developer in one summary. Developer says it's approved.

## Deviations

1. **The acceptance target is the fixture, not a repo the developer named.** Step 1 says to ask
   which repo to wire; the developer had already answered that for this project — the toolkit is
   being built without a real target ("real project later"), so `/Users/matt/Test/aw-fixture` (the
   `fixture` workspace registered by T13) *is* the target. Nothing was asked, and Steps 1–2 were
   therefore skipped: the fixture already has a hand-written `aw.config.json`, a React/Vite
   frontend on 5173 and a dependency-free API on 3001, so there was nothing to `aw init` and no
   framework to choose. Step 3 onward ran exactly as written.

2. **`design-loop` now states the screenshot procedure as an ordered list, and nudges once when a
   session produced none** (`src/workflows/design-loop.ts`). The first acceptance run implemented
   the page correctly and then wrote its summary without opening the browser at all — the
   screenshot rule was one bullet in the middle of a long "how to work here" list, and a 30B local
   model reads the end of a prompt best. The rule is now the last thing in the session prompt, as
   five numbered tool calls. Belt and braces: a session that produced no screenshot **of its own**
   gets exactly one `buildNudgePrompt` turn before the run fails with the existing `agent finished
   without screenshots`. That mirrors the single format retry `review` and `test-feature` already
   do, and it is strictly cheaper than re-running a whole implementation pass. In the re-run the
   prompt change alone was enough and the nudge never fired; it stays as the safety net for the
   next model that skips the step. Two properties of the nudge are enforced rather than asked for:
   - **it is gated on freshness, not on existence.** `shots.length === 0` could never fire on an
     `--iterate` run, because `--iterate` reuses the slug and the directory already holds the
     first pass's PNGs — exactly the run whose evidence failed during this acceptance. The gate is
     now "no PNG under the slug directory is newer than this session".
   - **it cannot become a second implementation pass.** It gets the browser tools (the same
     instances, so a re-shot screen keeps its file name) plus the read-only `reviewer` core
     profile — no `write_file`, `edit_file` or `bash` — and `NUDGE_MAX_STEPS` (12) rather than the
     session's 60. Previously only the prompt sentence "Do NOT edit any file now" stood between
     the nudge and the full designer tool set, while `git add -A` swept anything it wrote into the
     checkpoint.
   Verified against a stub provider on a repo whose only PNG was an hour old: the nudge fired
   (`warning: the session produced no new screenshot (only PNGs from an earlier run)`), where the
   previous gate would have skipped straight to presenting that PNG as evidence.

3. **`browser_screenshot` refuses a viewport with no successful navigation**
   (`src/tools/browser.ts`). Each viewport is its own Playwright context, so `browser_goto` on
   mobile leaves desktop at `about:blank`. The first `--iterate` run shot the desktop viewport
   without navigating it, and the tool cheerfully wrote a 5851-byte blank white PNG which the
   workflow then presented as proof the heading had changed. Silent blank evidence is the exact
   failure this workflow exists to prevent, so the tool now returns an error naming the missing
   call — `browser_goto {"url":"…","viewport":"desktop"}` — instead of a screenshot, the tool
   description says viewports are separate windows, and both design-loop prompts now walk
   goto→shoot per viewport. Refusal beats auto-navigating to the last URL: a screenshot must show
   a page the agent actually asked for. The step was re-run from the reverted tree, and the new
   `placeholder-desktop.png` renders the page.

   The guard tracks navigation **success per viewport** rather than inferring it from
   `page.url()`. Testing the URL against `about:blank` only caught a viewport that had never
   navigated at all: after a `browser_goto` that FAILED (dev server not up yet, restarted
   mid-loop, wrong port), Chromium shows a blank page while `page.url()` reports the URL it could
   not load, so the guard passed and a blank PNG was written and presented — the same artifact the
   guard exists to prevent. Reproduced live against real Chromium (goto ok → shot ok 5997 B; goto
   `ERR_CONNECTION_REFUSED` → shot **written**, 2538 B, blank). `makeBrowserActions` now keeps a
   `navigated` set, added on a resolved `page.goto` and deleted in its catch, and `screenshot`
   refuses unless the viewport is in it (the `about:blank` check is kept as a second gate). Same
   probe after the fix: the second screenshot returns the refusal and no file is written.

4. **Provider errors now quote what the provider said** (`src/workflows/common.ts`, new
   `providerDetail` + `isContextOverflowError`, new `src/workflows/common.test.ts`). `aw review`
   died with the single line `Bad Request` — the AI SDK puts the HTTP reason phrase in
   `error.message` and the server's actual explanation in `error.responseBody`, which nothing
   read. `describeModelFailure` now appends `provider said: HTTP 400 — <message>`, unwrapping the
   `{"error": …}` envelope, and that is what identified the real cause in one run. All three
   workflows share the helper, so all three gained the detail. The suffix is skipped when the
   extracted text is already inside `error.message` (the standard `{"error":{"message":…}}`
   envelope, which the AI SDK lifts into the message itself) — only the status is appended then,
   so the enveloped form no longer stutters while LM Studio's string form still gains everything.

5. **`aw review` shrinks the diff and retries when the model's context cannot hold it, and packs
   the budget smallest-file-first** (`src/workflows/review.ts`). Two separate defects behind one
   symptom:
   - The 60 KB cap of T08 step 3 is a cap, not a promise the model can read 60 KB. This branch's
     25.7 KB diff overflowed the 8192-token context of the configured LM Studio model and the
     whole review was lost. On a context-overflow error the workflow now halves the budget (at
     most 3 times, floor 2 KB), re-collects, says so on stderr and asks again; anything else, or
     a floor hit, still fails with the provider's own explanation plus "load the model with a
     larger context length, or review a narrower range with --base". Raising LM Studio's context
     would also fix it, but that is the developer's setting to change, not the toolkit's — and a
     tool that dies on a medium-sized branch is not usable locally.
