# T21 — Workspace & agent settings management

Depends on: T17. Read first: `tasks/SPEC.md` (AwConfig, Storage).
Goal: manage workspaces and per-agent provider/model/guardrail settings from the UI.

## Steps

1. `/settings` page with workspace tabs. Per workspace, a form (client component) bound to
   its `aw.config.json`:
   - defaults provider (select of the 4) + model (text input)
   - per-agent overrides (3 rows: agent, provider select incl. "inherit", model)
   - app block: backend/frontend start commands + ports, baseUrl, healthPath, staging URL,
     test account user + passEnv NAME
   - viewports (4 number inputs), offLimits (one per line textarea)
2. API routes (server, all zod-validated, path-confined to known workspaces):
   - `GET/PUT /api/config?ws=` — read/write `<repoRoot>/aw.config.json`. PUT: validate with
     `AwConfig.parse`; on success write pretty JSON and return it; on zod error return 400
     with issues rendered next to the form fields.
   - `POST /api/workspaces` — register existing repo (name + repoRoot; verify `.git` and
     `aw.config.json` exist, else 400 telling them to run `aw init`).
   - `DELETE /api/workspaces?name=` — removes the entry from `workspaces.json` ONLY (never
     touches the repo or run history); confirm dialog states exactly that.
   - `DELETE /api/runs?ws=&run=` — deletes one run directory (recursive) after a confirm
     dialog naming the runId; also `POST /api/runs/archive?ws=&run=` → moves the run dir to
     `<awHome>/<ws>/archive/`.
3. Runs table (T17) gains per-row Archive and Delete buttons wired to those routes;
   archived runs get an `/ws/[ws]?archived=1` toggle view (read from `archive/`).
4. Warning banner on the provider row when `claude-cli` is chosen for any CLI-run agent:
   "claude-cli works only via the .claude/ native path — CLI runs will refuse it."

## Acceptance

1. Change code-reviewer to `anthropic`/`claude-sonnet-5` in the UI → `aw.config.json` on
   disk shows it → next `npx tsx src/cli.ts review …` run's manifest records that
   provider/model.
2. Submitting an invalid config (e.g. empty model with non-default provider, port as text)
   shows a field error and writes nothing.
3. Delete a run from the UI → its directory is gone; archive → it moved under `archive/`
   and appears only in the archived view.
4. Registering a repo without `aw.config.json` returns the "run aw init" message.

## Out of scope
No secret storage of any kind (keys stay in shell/.env). No repo file editing beyond
`aw.config.json`.

## Deviations

1. **Two bugs were found by the verification and fixed, not worked around.**
   (a) `mergeConfig` wrote the patch object wholesale when the key did not exist yet, so the
   form's "no override" `null`s landed in the file as `"agents": { "ui-designer": null, … }` — a
   config `AwConfig` then rejects, i.e. one Save would have made the page unable to save again.
   It now recurses into `{}` so nulls are always applied as deletions, and drops a subtree the
   patch emptied instead of writing `{}`. Four unit tests cover it.
   (b) The confirm dialog's prose rendered as one long line spilling across the table, because
   `RunActions` lives in a `<td class="whitespace-nowrap">` and `white-space` inherits straight
   through `position: fixed`. The actions cell lost `whitespace-nowrap` (its buttons are flex
   items) and `ConfirmDialog` sets `whitespace-normal` on its panel, since it can be opened from
   anywhere. Both were invisible to DOM assertions and only showed up in a screenshot; the
   Playwright pass now asserts the dialog's `scrollWidth <= clientWidth`.

2. **Numeric fields are `type="text" inputMode="numeric"`, and the form is `noValidate`.**
   `type="number"` discards a non-numeric value before it can be submitted, and the browser's own
   constraint validation *blocks* the submit entirely (found the hard way: with `pattern="[0-9]*"`
   the Save button did nothing and no request was made). Acceptance 2 requires "port as text" to
   produce a FIELD ERROR, which means the value has to reach the server. One validator — the one
   that owns the file, and the same schema the CLI uses — beats two that disagree.

3. **`configRuleIssues()` mirrors rules `AwConfig` cannot express.** `ModelChoice.model` is
   `z.string()`, so `""` passes the schema; an empty model is only wrong when something tries to
   *resolve* it, and that logic lives in `src/config.ts`, which the panel may not import (node-only
   neighbours). The two resolution rules of SPEC § Model resolution are therefore re-stated in
   `dashboard/src/lib/config-patch.ts` — with the CLI's exact message for the one the CLI prints —
   alongside the guards `aw init` applies to its flags (a port is 1–65535, `passEnv` is an
   identifier). They run on the merged object before any write.

4. **Config writes match `aw init`'s two properties, deliberately.** The patch is merged into the
   RAW parsed JSON (never into `AwConfig.parse()`'s output, which would strip hand-added keys),
   and a save that changes nothing writes nothing, so a hand-formatted file stays byte-identical.
   A save that DOES change something re-serialises with two-space indentation — exactly what
   `aw init` does when its merge adds a key.

5. **Mutating routes require a same-origin-looking request (beyond the task list).** Loopback is
   not the same as same-origin: any web page in another tab can `fetch('http://127.0.0.1:4400/api/
   runs?…', { method: 'DELETE' })` from the user's own machine. `guardMutation()` (
   `dashboard/src/lib/api-guard.ts`) refuses a request whose `Origin` does not match the host it
   was addressed to, refuses `Sec-Fetch-Site: cross-site`/`same-site`, and refuses the three
   content types an HTML form can post. `curl` (no browser headers) still works, which is what the
   probes rely on. SPEC invariant #1 covers the network; this covers the browser.

6. **A config that ALREADY contains a secret-shaped key is refused, not rewritten.** SPEC
   invariant #5 says a config write must never persist a password or key; T21 also says a
   developer's hand-added keys must survive. Those conflict for a file containing
   `"password": "…"`, so PUT answers 400 naming the key and asks for it to be moved into an
   environment variable — it neither stores the secret nor silently deletes their key.
   `passEnv` is explicitly not matched: the NAME is the safe thing.

7. **Archive got a Restore, and Delete deliberately did not get an `area` parameter.**
   A one-way archive button with no way back short of a terminal is a trap, so
   `POST /api/runs/archive?…&action=restore` is the same `rename` with the two directories
   swapped, through the same gate. `DELETE /api/runs` on the other hand takes only `ws` and `run`
   and hard-codes `runs/`, so the only directory it can ever name is
   `$AW_HOME/<ws>/runs/<runId>` — an archived run has to be restored before it can be deleted.

8. **Destructive operations use a stricter gate than reads.** `realRunDir()` (T17, reads) asks
   "does this resolve inside the store?", which is right for serving bytes but also describes
   another workspace's run — a `runs/<id>` symlink pointing at a sibling run would pass it and
   `rm -r` would take the sibling with it. `mutableRunDir()` instead `lstat`s the entry (a symlink
   is refused, never followed) and proves the path is EXACTLY
   `<realpath($AW_HOME)>/<ws>/<area>/<runId>`, segment by segment, including that its
   great-grandparent is the store root. The read path is unchanged.

9. **Archived runs are listed unlinked.** `/ws/[ws]/run/[id]` reads `runs/`, so a link to an
   archived run would answer 404; the row shows the id as plain text plus a Restore button. Home's
   "latest runs" table gets no action buttons at all — it spans workspaces and is a glance
   surface, not a place to be one misclick from deleting a run you were only looking at.

10. **Registration validates more than existence.** T21 asks for `.git` + `aw.config.json` (both
    checked, with the "run aw init" message). It also requires the config to parse as `AwConfig`
    and to declare the same workspace name, because `--workspace <name>` resolves the repo through
    the registry and then takes the workspace identity from the FILE: a disagreement silently
    files runs under a different name. Both refusals name the field the form should highlight.

11. **A `settings` link was added to the site header and to the workspace page header.** Those two
    files are outside the strict letter of this task's scope, but `/settings` had no link from
    anywhere and a local tool whose configuration is reachable only by typing a URL is not
    configurable.

12. **`vitest.config.ts` was added at the repo root.** `config-patch.ts` is the first module to
    import `AgentName`/`ProviderId` from `@shared/schemas` as VALUES (zod enums: the form renders
    `.options`, the patch schema keys a record by them); every earlier test used `import type`,
    which is erased before anything has to resolve the alias. The config adds the two aliases
    `dashboard/tsconfig.json` already declares and changes nothing else — no new dependency, same
    include patterns, same 443 pre-existing tests passing.

13. **The first verification passes ran on port 4401, from an rsync'd copy of the repo.** A
    parallel session (T20) held port 4400 and `dashboard/.next`, and Next 16 refuses a second
    `next dev` in the same directory. Once it exited, the probe pass, the visual pass, the CLI
    round trip and every screenshot in this file were re-run from the real repo on port 4400; the
    copy has been deleted.

14. **Everything destructive ran against a COPY of `$AW_HOME`.** The seeded runs were never
    archived, deleted or moved. The one thing that had to be the real object is the fixture repo's
    `aw.config.json` (the round trip is only meaningful against the repo the registry points at) —
    it was backed up first and restored byte-for-byte, and `git status` in that repo is clean.

15. **Not done, deliberately:** `/api/runs` has no `GET` (T22 owns run polling), the settings page
    does not offer to CREATE a config (that is `aw init`'s job — the panel says so instead), and
    an archived run has no detail page.

16. **`writeConfigFile` writes the repo's `aw.config.json` through a temp file + `rename`**, which
    `aw init` does not (it writes in place and reserves tmp+rename for `$AW_HOME`). Atomicity is
    worth more here than there: the CLI re-reads that file mid-run, so a half-written config is a
    failed run. The cost is possible crash residue in a directory under git, so the temp name is
    dot-prefixed (`.aw.config.json.tmp-<pid>`) and unlinked on every failure path.

## Corrections (2026-08-22, review follow-up)

- **Deviation 8's gate covered only the SOURCE of a move.** `moveRun` built the destination with
  `path.join(mutableWorkspaceDir(ws), to)`, and `rename(2)` follows symlinks in the path prefix —
  so a symlinked `$AW_HOME/<ws>/archive` moved the run OUT of the store and the route answered
  `{"ok":true,…,"movedTo":"archive"}`. `restore` then 404ed, because the source gate did its job:
  the run was gone from the active view, the archived view and the panel's reach, permanently.
  The destination now goes through `mutableAreaDir`, held to the same proof as the source
  (`mkdir`, then `lstat` + a `realpath` that must equal `<realpath($AW_HOME)>/<ws>/<area>`), and
  an existing destination is detected with `lstat` so a DANGLING link is not silently replaced
  either. `dashboard/src/lib/store.test.ts` is new and exercises both sides of the move, plus
  `deleteRun`, against a temp `$AW_HOME` with planted symlinks — the acceptance run's 97 probes
  had only ever planted them on the `runs/` side, which is why this survived.

- **The panel's cross-site defence did not pin the `Host` header.** `guardMutation` compared
  `Origin` against the `Host` the request carried, which under DNS rebinding is a name the
  attacker controls on both sides. Verified before the fix: a request with
  `Host: attacker.example:4455`, `Origin: http://attacker.example:4455` and `Sec-Fetch-Site:
  same-origin` rewrote `aw.config.json`, spawned a workflow, deleted a run directory and streamed
  a run log — and since `app.backend.start` is persisted config that `ensureUp()` later hands to
  `spawn(…, { shell: true })`, the config write chains to command execution. `guardHost` now
  refuses any `Host` that is not `127.0.0.1`, `localhost` or `[::1]` (widenable with
  `AW_DASHBOARD_HOSTS`), and it is called from `guardMutation`, from the read routes and from a new
  `dashboard/src/middleware.ts` that fronts every route and page so a route added later cannot
  forget it.

- **Run rows address a run by the DIRECTORY they were read from.** `run-table.tsx` passed
  `manifest.runId`/`manifest.workspace` to Archive and Delete, and a manifest is untrusted run
  content: `cp -R` of a run directory made either row's Delete remove the ORIGINAL. `loadManifest`
  now derives both fields from the path, so every consumer at once — table, actions, artifact
  links, `/api/feedback` — can only name the directory the bytes came from.

- **`/settings?ws=<unknown>` answers 404** instead of silently falling back to the first
  workspace, which rendered another repo's `aw.config.json` in an editable form whose Save wrote
  to that other repo. `/ws/[ws]` and `/api/config` already refused unknown names.

- **Workspace summaries carry `archivedCount`.** The "forget this workspace" dialog promises that
  the runs in the store stay as they are, and `listRuns` walks only `runs/` — a workspace whose
  runs had all been archived read as "0 recorded runs".
