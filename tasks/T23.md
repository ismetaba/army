# T23 — Split the workspace into a backend set and a frontend set

Depends on: T01–T22 (all done). Read first: `tasks/SPEC.md`, then this whole file.
Goal: one workspace can describe a product whose backend and frontend live in **two different
repositories**, and each workflow runs against the right one automatically.

## Why (the concrete failure this fixes)

A workspace is currently one repo: `AwConfig.repoRoot`, plus an optional `app` block that
assumes the backend and the frontend are both inside it.

The developer's real product is not shaped like that:

| | repo | what it is |
|---|---|---|
| backend | `/Users/matt/custody` | Java / Maven, the API under test |
| frontend | `/Users/matt/Project 1/cus-admin-ui` | Angular (`npm start`, port 4200) |

Registering `custody` and asking for a UI task produced this, and nothing else:

```
[runner] argv[2]="design-loop"
[runner] argv[3]="I need a list page of qarantined transaction. The ui is here: /Users/matt/Project 1/cus-admin-ui"
no frontend URL: configure app.frontend.port (or app.baseUrl) in aw.config.json
[runner] exited code=1 (no run id was announced)
```

The developer had to say where the UI was **in the prompt**, because the config had nowhere to
put it. Registering the two repos as two separate workspaces does not fix it either: the UI
workspace then has no idea what API the page must call, and the backend workspace has no UI to
screenshot. The two halves have to be one workspace with two targets.

## What to build

### 1. Config shape (`shared/schemas.ts`)

Replace the single `repoRoot` + flat `app` with two **target sets**. Both are optional; a
workspace may have one or both.

```ts
const Target = z.object({
  repoRoot: z.string(),                 // absolute path — its own git repo
  start: z.string().optional(),         // dev-server command, run in repoRoot
  port: z.number().optional(),
  url: z.string().optional(),           // defaults to http://localhost:<port>
  healthPath: z.string().optional(),    // backend only in practice; keep it on both
});

// inside AwConfig:
  backend: Target.optional(),
  frontend: Target.optional(),
```

`testAccount`, `stagingUrl`, `viewports` and `offLimits` stay where they are — they are
workspace-wide, not per-target.

**Migration is mandatory and must be silent.** Every existing `aw.config.json` in the wild
(`fixture`, `gold-token`, `custody`, `cus-admin-ui`) uses the old shape. Write a
`migrateConfig()` that maps old → new **on read**, so an unmigrated file keeps working:

- `repoRoot` + `app.backend` → `backend: { repoRoot, ...app.backend }`
- `repoRoot` + `app.frontend` → `frontend: { repoRoot, ...app.frontend }`
- `app.baseUrl` → `backend.url`
- `repoRoot` with no `app` at all → `backend: { repoRoot }` (the review-only case: `custody`)

Do **not** rewrite files on read. `aw init` and the panel's settings save write the new shape;
everything else migrates in memory. Keep `AwConfig.repoRoot` readable as a **derived** value —
`backend?.repoRoot ?? frontend?.repoRoot` — because ~20 files consume it (see § Blast radius)
and forcing every one of them to choose a target in this task would be a much riskier change.

### 2. Which target each workflow uses

This is the heart of the task. Each workflow gets ONE **primary target** — the repo it reads,
edits, commits in, and whose root bounds the file tools — and may be **told about** the other.

| workflow | primary target (cwd, git, tool containment) | also told about |
|---|---|---|
| `design-loop` | **frontend** — this is where the UI is written, screenshotted and checkpointed | the backend's `url` + `healthPath`, in the prompt, as the data contract the page calls |
| `test-feature` | **backend** — the target URL it exercises | the frontend `url`, only when the case needs the browser |
| `review` | **whichever the run names** — see below | — |

`review` reviews a diff, and a diff belongs to one repo. Add `--target backend|frontend`
(default: `backend` if present, else `frontend`). The panel's create-task slip gets the same
choice as a segmented control, but only when the workspace actually has both.

Failure messages must name the missing piece precisely — the current one
(`no frontend URL: configure app.frontend.port`) was right in kind and is the model to follow:

- design-loop with no `frontend`: *"this workspace has no frontend target — add one in settings
  (repo folder + start command + port), or run design-loop in a workspace that has one"*.
- test-feature with no `backend` and no `--url`: same shape.
- review with `--target frontend` when there is no frontend: same shape.

### 3. Starting the right servers

`ensureUp()` (`src/util.ts`) currently starts what the flat `app` block described. It must now
start **per target**:

- design-loop starts the frontend (and the backend too, if configured — the page it builds has
  to have something to fetch from; that is why the backend url is in the prompt).
- test-feature starts only the backend it is targeting.
- review starts nothing (unchanged).

Each spawn uses **that target's own `repoRoot` as cwd**, not the workspace's. This is the bug
that makes the current shape unfixable: one `repoRoot` cannot be the cwd for `mvnw spring-boot:run`
and for `ng serve` at the same time.

### 4. Tool containment (`src/tools/core.ts`) — read this carefully

`makeCoreTools(profile, repoRoot)` confines every path to one root. With two repos, the
design-loop agent legitimately needs to READ the backend (to learn the API contract) while
being allowed to WRITE only in the frontend.

Implement it as: **write inside the primary target only; read inside either target.** Signature
becomes `makeCoreTools(profile, { primary, readAlso })`. Every existing guarantee stays —
`..` escapes, symlinks out, absolute paths, the blocked bash patterns, the destructive-HTTP
gate. Add tests that pin the new rule: a write into `readAlso` must be refused with a message
naming which root is writable.

`bash` runs with cwd = primary. `git_diff` / `git_log` stay on the primary — a diff of the
other repo is a different run.

### 5. `aw init` (`src/commands/init.ts`)

Today it takes one repo. It must be able to describe both halves in one go:

```
--backend-repo <path>  --backend-start <cmd>  --backend-port <n>  --health-path <p>
--frontend-repo <path> --frontend-start <cmd> --frontend-port <n>
```

Rules that must not regress: `--yes` never blocks; nothing is written until everything is
planned and proven writable; an existing config is merged, never clobbered; no password is ever
asked for or stored (only `passEnv`). Each target's repo must exist and contain `.git` —
report which one failed by name.

`.claude/` and `CLAUDE.md` get copied into **both** repos when both are given: whichever repo a
developer opens, the slash commands should be there.

### 6. The registry (`$AW_HOME/workspaces.json`)

`Workspace` is `{ name, repoRoot, createdAt }`. Widen it to carry both roots — the panel needs
them to render a workspace and to spawn with the right cwd:

```ts
{ name, backendRepo?: string, frontendRepo?: string, repoRoot: string /* kept: = backend ?? frontend */, createdAt }
```

Keep `repoRoot` populated so an older panel build and every current consumer keep working.
Tolerate an entry that has only the old field (that is what is on disk now).

### 7. The panel

- **Settings** (`dashboard/src/app/settings/config-form.tsx`): the `App` section becomes two
  ruled sub-sections, `Backend` and `Frontend`, each with repo folder / start command / port /
  URL (+ health path on backend). Follow the Ledger design already in place — underline fields,
  no boxes, mono labels. A target with no repo folder is simply absent; do not write an empty
  object into the config.
- **Entry + top bar**: a workspace with two repos shows both paths (the entry row's second line
  is currently one path; make it two lines or `backend · frontend`).
- **Create-task slip**: the `review` form gains the `TARGET` segmented control from § 2, shown
  only when both targets exist. `design-loop` and `test-feature` need no new field — they infer
  it — but the slip's `WILL RUN` preview must show the resolved `--target` when it is not the
  default, because that preview is a promise about the command that runs.
- **Task detail header**: the meta row shows which repo the run acted on. It currently shows
  `BASE` for review; add `TARGET` (`backend` / `frontend`) for every kind.
- `dashboard/src/lib/runner.ts` spawns with `cwd` = **the primary target's repoRoot for that
  kind**, not the registry's single `repoRoot`. This is the panel-side half of § 3 and the one
  place a mistake means the CLI runs in the wrong repository.
- `dashboard/src/lib/trigger-args.ts`: add `target` to the review kind's ARGUMENT ALLOWLIST.
  It is a fixed enum, so validate it as one — never pass an arbitrary string through.

### 8. Run manifests (`shared/schemas.ts`, `src/store.ts`)

Add `target: 'backend' | 'frontend'` and the resolved `repoRoot` to `RunManifest.input`, so a
finished run says which repo it touched. Existing manifests lack it — parse it as optional and
render "—" rather than failing (the store already refuses to throw on an unreadable manifest;
keep that).

## Blast radius (do not discover this halfway)

`repoRoot` appears in 21 non-test files. The heavy ones:

```
30  src/workflows/design-loop.ts      30  src/commands/init.ts
27  src/workflows/review.ts           15  src/workflows/test-feature.ts
11  src/tools/core.ts                 10  dashboard/src/lib/runner.ts
10  dashboard/src/app/settings/workspace-registry.tsx
10  dashboard/src/app/api/workspaces/route.ts
 8  dashboard/src/components/entry/add-workspace.tsx
```

Keeping `repoRoot` as a derived value (§ 1) is what stops this from becoming a rewrite of all
21. Change a file only where it genuinely needs to know WHICH target.

## Out of scope

More than two targets. Monorepo sub-paths (one repo, two directories) — the shape below would
support it since each target carries its own `repoRoot`, but do not add UI for it.
Changing the agent prompts in `agents/*.md`.
