# T13 — `aw init` workspace onboarding

Depends on: T03, T11. Read first: `tasks/SPEC.md` (AwConfig, Storage, Workspace).
Goal: point the toolkit at any target repo in one command.

## Steps

1. Create `src/commands/init.ts` → `registerInit(program)`; register in cli.ts. Options
   (all optional; missing ones asked interactively via `node:readline/promises`, with the
   shown defaults):
   - `--repo <path>` (default: cwd) — must contain `.git`, else exit 1.
   - `--name <ws>` (default: repo dir name)
   - `--backend-start`, `--backend-port`, `--health-path` (default `/health`)
   - `--frontend-start`, `--frontend-port`
   - `--base-url` (default `http://localhost:<backend-port>`)
   - `--test-user`, (password: NEVER asked/stored — print `set AW_TEST_PASSWORD in your shell/.env`)
   - `--staging-url` (default: none)
   - `--provider` + `--model` for defaults (default `lmstudio` + ask model id)
   - `--yes` = non-interactive, use defaults, skip unanswered optionals.
2. Actions, in order:
   1. Build an `AwConfig`, validate with zod, write `<repo>/aw.config.json`
      (exists → show diff-style summary and ask before overwrite; with `--yes` keep existing
      and only ADD missing keys).
   2. Register workspace in `$AW_HOME/workspaces.json` (create file/dirs; replace entry with
      same name).
   3. Copy `.claude/agents/*` and `.claude/commands/*` from THIS repo into the target's
      `.claude/` (create dirs; never overwrite an existing same-named file — print `kept
      existing: <path>`).
   4. CLAUDE.md merge: if target has none, create a minimal one (project line + Commands +
      guardrails). If it exists, append ONLY a marked block, replacing a previous one:
      ```
      <!-- aw:start -->
      ## Agent workflows (aw)
      ...commands, screenshot/report conventions, guardrails...
      <!-- aw:end -->
      ```
   5. Ensure target `.gitignore` contains `screenshots/`, `test-reports/`, `.env`
      (append missing lines only).
3. Print a summary tree of every file created/modified in the target repo.

## Acceptance

```
mkdir -p /tmp/aw-scratch && cd /tmp/aw-scratch && git init -q
npx tsx <this-repo>/src/cli.ts init --yes --name scratch --provider lmstudio --model test-model
```
1. `aw-scratch` now has: valid `aw.config.json` (zod-parses), `.claude/` with 6 files,
   CLAUDE.md containing the `<!-- aw:start -->` block, updated `.gitignore`.
2. `~/.agent-workflows/workspaces.json` lists `scratch` with the right `repoRoot`.
3. Running init again with `--yes` is idempotent (no duplicate blocks/lines; `kept existing` messages).

## Out of scope
No workflow runs. Dashboard reads workspaces.json later (T17).

## Deviations

1. **The whole run is planned before a single byte is written.** `planInit()` asks every
   question, reads every file, computes every merged result and finally proves every destination
   that will actually change can be written (`writabilityProblem()` — an existing file must be
   `W_OK`, and no ancestor of a planned path may be a regular file). `applyPlan()` then applies
   the plan in its own order: writes (`aw.config.json`, `CLAUDE.md`, `.gitignore`), then the
   `.claude/*` copies, then `workspaces.json`. That is *not* step 2's order, and it does not need
   to be: nothing is computed during apply, so the ordering of the writes is immaterial —
   what step 2's ordering was protecting against is instead prevented by there being no reachable
   partial state. Without the split, a malformed `CLAUDE.md` (step 2.4) would abort a run that had
   already rewritten `aw.config.json` and `workspaces.json`. Verified: an unclosed marker, a
   read-only `CLAUDE.md`, and a `.claude` that is a regular file each exit 1 with
   `Nothing was written.` and leave the target repo byte-identical. Should a write still fail
   (a race with another process, a full disk), `applyPlan` rethrows it as an `InitError` naming
   the file, the step, and every file already written — never a bare `EACCES: permission denied`.

2. **A non-TTY stdin is treated exactly like `--yes`.** The readline interface is created lazily
   and only when `!--yes && process.stdin.isTTY`, so no prompt object exists in a piped run and
   there is nothing that *could* block. `init … < /dev/null` without `--yes` completes in 0.6 s
   with `note: stdin is not a TTY — running non-interactively with the defaults (as with --yes)`.

3. **`--pass-env <VAR>` added** (not in the option list). `AwConfig.app.testAccount` requires
   `passEnv`, so `--test-user` alone cannot produce a valid entry, and a user whose variable is
   not `AW_TEST_PASSWORD` had no way to say so. It is validated as an identifier
   (`/^[A-Za-z_][A-Za-z0-9_]*$/`) so a pasted password is rejected rather than written. There is
   deliberately no flag, prompt or env read that could carry a password *value*.

4. **The registered workspace name is the one the written config declares, not `--name`.** When
   an existing `aw.config.json` says `workspace: "fixture"` and the flag says something else, the
   file wins and a `note:` says so. Registering the flag's name would produce a `--workspace`
   entry pointing at a config that disagrees with it, and every workflow reads the name from the
   config. The name is also validated as a single safe path segment, since it becomes a directory
   under `$AW_HOME`.

5. **The RAW merged JSON is written, never the zod-parsed copy.** `AwConfig` is a plain
   `z.object`, so `parse()` strips unknown keys — writing the parsed result would silently delete
   any key a developer added by hand. The parsed copy is used only to validate and to read back
   `workspace`/`repoRoot`/`passEnv`.

6. **A config that needs nothing added is left byte for byte alone.** Re-serialising with
   `JSON.stringify(…, 2)` turned the fixture's compact hand-written config into a 30-line diff
   while changing no value. Reformatting is not a merge result, so when the merge adds nothing the
   original text is kept. (This is why the fixture's `aw.config.json` md5 is unchanged.)

7. **Interactive overwrite defaults to "keep".** Step 2.1 says an existing config prompts before
   overwrite; the diff-style summary is printed and the default answer is `n`, which takes the
   `--yes` path (keep existing, add missing keys). No answer can ever silently clobber values.

8. **`createdAt` of an existing same-name workspace entry is preserved on replace.** Re-running
   init re-points a workspace, it does not re-create it — and preserving the timestamp is what
   makes the rewritten `workspaces.json` byte-identical, i.e. genuinely idempotent.

9. **A corrupt `workspaces.json` is salvaged, not discarded.** Invalid JSON or a drifted shape no
   longer stops init: individually valid entries are kept, the original is copied to
   `workspaces.json.corrupt-<ms>`, and a `warning:` names what was dropped. Verified against a
   file containing one good entry, one entry missing `repoRoot`, and the number `42`.

10. **`.gitignore` matching is loose on purpose.** A leading `/` and a trailing `/` are ignored
    when deciding whether a line is already present, so an existing `/screenshots` does not gain a
    duplicate `screenshots/`. A comment (`# test-reports/`) or a negation (`!screenshots/`) never
    counts as present — it means the opposite. Existing bytes are never rewritten; only missing
    lines are appended, after repairing a missing final newline.

11. **`--backend-port` / `--frontend-port` without the matching `--*-start` is an error.**
    `AwConfig` requires `start` for both blocks, so a port alone cannot produce a valid `app`
    entry. With `--yes` and no start command, the whole `app` block is skipped, per "skip
    unanswered optionals".

12. **With `--yes` and no `--model`, `defaults.model` is written as SPEC's example
    `qwen3-30b-a3b`** and a `warning:` says to replace it with the id shown in LM Studio's UI.
    Non-interactive means "take the default"; a config without `defaults.model` would not parse.
    The warning is emitted *after* the merge and only when the value that will actually be written
    is the placeholder: emitting it before the merge announced a default on every re-init of a
    repo whose config already named a real model, which trains the user to ignore a line that is
    load-bearing on a first run.

13. **A newly created `CLAUDE.md` gets a two-line header above the block.** Step 2.4's "project
    line + Commands + guardrails" is satisfied by the header (project line) plus the marked block
    (commands, artifact conventions, guardrails). Keeping Commands and guardrails *inside* the
    markers is what lets a later init refresh them without touching the developer's own notes.

14. **Recorded `repoRoot` is `path.resolve()`d, not `realpath()`ed.** Running the acceptance from
    `/tmp/aw-scratch` therefore records `/private/tmp/aw-scratch`, because Node's `process.cwd()`
    already resolves the macOS `/tmp -> private/tmp` symlink. Same directory, canonical spelling.

15. **The registry is re-read and rewritten atomically at apply time.** `planInit` computes the
    upsert to validate and to size the write, but `applyPlan` re-reads `workspaces.json`, re-runs
    `upsertWorkspace`, and installs the result with `write tmp-<pid>` + `rename`. Reusing the
    plan-time snapshot would erase a workspace another `init` registered in between, and a direct
    `writeFileSync` leaves a reader a truncated file. The file is still left alone byte for byte
    when the content is unchanged, which is what keeps a second `aw init` idempotent.

16. **The generated `CLAUDE.md` block derives the runs path from `awHome()`.** It used to print
    `~/.agent-workflows/<ws>/runs/` literally, which names the wrong directory for anyone running
    under `AW_HOME`. The toolkit checkout path in the same block is still absolute (the commands
    have to be copy-pasteable) but now says out loud that it is local to whoever ran `aw init`.

17. **`AW_HOME` pointing at a regular file is reported as such.** The registry read used to fail
    with a bare `ENOTDIR` that never mentioned `AW_HOME`; it now says `AW_HOME must be a
    directory, but <path> is not one` and ends with `Nothing was written.`, like every other
    planning failure.

18. **`repoRoot` is the one key the existing file does NOT win.** It is derived from the
    invocation, not authored: an absolute, machine-specific path inside a file that gets committed,
    so every clone, move or second machine arrives with a value pointing somewhere else. Letting it
    through the ordinary merge registered the workspace against the *other* repo — reproduced with
    a config declaring `…/other` while `…/moved` was inited: `init` exited 0 saying
    `workspace "team" registered`, and `review --workspace team` then reviewed `…/other` (or died
    with `config not found` when the stale path did not exist). Now, when the declared `repoRoot`
    does not resolve to the repo being inited, it is rewritten to the resolved target, stderr says
    `note: … repoRoot pointed at <old> — updated to <new>`, and the summary carries
    `config repoRoot corrected: <old> → <new>`. The registry entry uses the directory that was
    inited, never the value the file carried, and the summary's registration line now names it.
    (Unlike the workspace NAME in deviation 4, `repoRoot` is not an identity a developer chooses —
    there is nothing for them to mean by it other than "this repo".)
