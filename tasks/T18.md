# T18 — Review UI (Bitbucket-like)

Depends on: T17. Read first: `tasks/SPEC.md` (Finding, Review output contract).
Goal: diff viewer with findings pinned inline at file:line.

## Steps

1. `dashboard/src/lib/diff.ts`: parse a unified diff (`artifacts/diff.patch`) into
   `{ file: string; hunks: { header: string; lines: { type: 'ctx'|'add'|'del'; oldNo?: number; newNo?: number; text: string }[] }[] }[]`.
   Write it by hand (~60 lines: track `@@ -a,b +c,d @@` counters); add a vitest with a small
   fixture diff asserting line numbers.
2. Run page `Review` tab (only when `manifest.review` exists), client component:
   - Verdict banner: green APPROVE / yellow APPROVE WITH NITS / red REQUEST CHANGES.
   - Severity filter chips with counts: BLOCKER / MAJOR / MINOR / NIT (toggle, all on by default).
   - Per changed file: collapsible section, unified diff table — line numbers (old/new),
     `+` rows green-tinted, `-` rows red-tinted, monospace, horizontal scroll inside the
     container.
   - Each finding renders as a card directly UNDER the diff row where `finding.file` matches
     the section and `finding.line` equals the row's NEW line number: severity badge, title,
     Risk, Fix (Fix in a copy-to-clipboard block). Findings whose file/line is not present in
     the diff render in an "Unanchored findings" list at the bottom (never drop them).
   - Sidebar list of all findings (sorted by severity) — clicking scrolls to the card
     (`element.scrollIntoView`).
3. Keep it dependency-free (no diff2html etc.) — Tailwind only.

## Acceptance

Using a real T08+T16 run that produced ≥2 findings of different severities:
1. Verdict banner matches the manifest; chips filter cards live.
2. A finding card sits under exactly the right diff line (verify against `diff.patch` by eye).
3. An artificially edited manifest finding with a bogus line shows under "Unanchored findings".
4. Wide diffs scroll horizontally inside the panel — the page body does not scroll sideways.

## Out of scope
No commenting/replying, no re-run button (T22), no side-by-side mode (unified only).

## Deviations

- **The default tab is still `log`.** `parseTab`'s comment says the default should move to the
  run's own type tab "when the type views land", but T19/T20 were being written against the same
  file at the same time and the switch is a decision for all three tabs at once, not for this one.
  The Review view is reached with `?tab=review` and from the tab bar.
- **Colour tokens live in `dashboard/src/components/review-theme.css`, not `globals.css`.** Same
  convention as globals.css (a `:root` block and a `prefers-color-scheme: dark` block, no `dark:`
  variants), but the file is scoped to this feature — `globals.css` was being edited in parallel,
  and diff tints and severity chips are read by nothing else. Green and red for APPROVE /
  REQUEST CHANGES are NOT redefined there; the view reuses `--done-*` and `--error-*`.
- **A file's diff is rendered as several tables, not one.** Step 2 asks for the finding card to
  sit under its diff row *and* for the diff to scroll horizontally inside its container. A card
  inside the scroller would slide off-screen with the code, so each file's rows are cut into
  segments at every anchored row: the rows scroll, the cards between them do not. The gutters get
  one fixed `ch` width per file so the segments still line up, and their scroll positions are
  synced so the file behaves as one table.
- **The parser returns a superset of the shape in step 1.** `{ file, hunks: { header, lines:
  { type, oldNo?, newNo?, text } } }` is all there, plus `oldPath`/`newPath`/`status`/`binary`/
  `truncated`/`additions`/`deletions` per file, `section` + the `@@` counters per hunk, and
  `noNewline`/`partial` per line — everything the header row and the truncation notice show.
- **Findings anchor on context rows as well as added rows** — step 2 says "the row's NEW line
  number", and an unchanged line inside a hunk has one. Removed rows have no new number and
  therefore never take a card.
- **Line-number gutters are `position: sticky`** (not asked for): on a wide line the numbers would
  otherwise scroll out of view, which defeats the point of showing them next to a finding.
- **Tab visibility stays kind-based, not data-based.** Step 2 says the Review tab shows "only when
  `manifest.review` exists"; `parseTab`/`visibleTabs` gate on `t.kind === run.kind`, which is
  T17's rule for all four tabs and the one place that decides tab visibility for T18/T19/T20
  alike. A `review` run that died before the reviewer reported therefore still offers the tab, and
  `ReviewTab` renders "This run recorded no review result." Gating one tab on its data and the
  other two on their kind would be the worse inconsistency; if it changes, it changes for all
  three at once, next to the default-tab switch above.
- **The severity chips filter the sidebar as well as the cards.** Step 2 says "sidebar list of all
  findings"; the sidebar is a jump list *to* the cards, so an entry whose card is filtered out
  would scroll to nothing. The chip counts are computed over the **unfiltered** set, so a hidden
  BLOCKER is still visible as a number on its chip and one click brings it back.
- **A finding's `file` anchors on an exact path first, then on a unique suffix match.** `matchFile`
  tries `file`/`newPath`/`oldPath` verbatim (after normalising `\` and a leading `./`), and only
  then accepts `norm.endsWith("/" + wanted) || wanted.endsWith("/" + norm)` — and only when
  **exactly one** file in the diff matches, so an ambiguous basename stays unanchored rather than
  landing on the wrong file. The tolerance is there because `finding.file` is model-written: a
  reviewer that says `server.mjs` or pastes an absolute path still pins to `api/server.mjs`.
- **An unreadable `diff.patch` reports its errno, not the fs message.** `err.message` carries the
  ABSOLUTE path for EACCES/EISDIR/ELOOP/ENAMETOOLONG/EIO, and SPEC § Dashboard security invariants
  #2 forbids an error naming a real path. The notice now reads
  `artifacts/diff.patch could not be read (EACCES) — findings cannot be pinned to a diff.`, which
  matches the wording of the "not in this run's directory" and "too large" branches beside it.
  `readLogTail` and the raw-report reader were given the same treatment.
- **The truncation marker is only honoured where `collectDiff` can emit one** — at EOF, or on the
  line immediately before the next `diff --git`. `TRUNCATION_MARKER` is end-anchored but not
  start-anchored (the marker can be glued to a half-written line), which also made it match a
  **reviewed file's own content** ending in that text: the file's diff ended there, its +/− counts
  went to zero, it was tagged "truncated", and every finding below the line lost its anchor.
- **The seeded-run tests use `describe.skipIf`.** They read the real
  `$AW_HOME/fixture/runs/review-20260822-004504`, so they are skipped rather than failing on a
  machine whose store does not have it. They ran (not skipped) for the acceptance below.
