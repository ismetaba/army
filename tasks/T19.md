# T19 — Test report UI

Depends on: T17. Read first: `tasks/SPEC.md` (TestCase).
Goal: tester findings readable at a glance, failures with exact evidence.

## Steps

1. Run page `Report` tab (only when `manifest.test` exists):
   - Summary header: `manifest.test.summary` + PASS/FAIL/SKIP counts + pass-rate bar.
   - Case table: id, name, kind badge (happy/edge/invalid/auth), status badge
     (PASS green / FAIL red / SKIP gray), severity badge for failures. Row click opens a
     detail drawer (client component): request and response in separate monospace
     `<pre>` blocks (scroll inside, copy button each), repro steps as an ordered list.
   - Filters: status (default: FAIL first, table sorted FAIL→PASS), kind.
   - "Raw report" section: render `artifacts/report.md` markdown. Use `marked` +
     `DOMPurify`? NO new deps — render it in a bordered `<pre>` (monospace, wrap) instead;
     good enough, dependency-free.
2. Feature history: under the table, list other runs of kind `test-feature` in the same
   workspace whose `input.feature`/`input.args` share the same slug, linked, with their
   pass counts — so regressions are visible run-over-run.

## Acceptance

With a real T09+T16 run containing ≥1 FAIL:
1. Counts and badges match the manifest; FAIL rows sort first.
2. The FAIL drawer shows the exact request and response strings from the manifest verbatim.
3. Raw report section shows the full report file.
4. A second run of the same feature appears in the history list of the first.

## Out of scope
No re-run triggering (T22), no editing.

## Implementation notes (done)

Files:
- `dashboard/src/components/report-panel.tsx` — server component: summary header + pass-rate bar,
  feature history, raw `report.md`. Reads the store; no client JS.
- `dashboard/src/components/report-cases.tsx` — the only client component: status/kind filters,
  case table, failure drawer, copy buttons.
- `dashboard/src/components/report-data.ts` — pure helpers shared by both (counts, sort order,
  feature slug). No React, no `node:`, so the client half stays free of `@/lib/store`.
- `dashboard/src/app/ws/[ws]/run/[id]/page.tsx` — one branch added to the tab body; the tab
  container, `TABS` and `parseTab` are untouched (T18 owns its own branch in parallel).

Decisions worth knowing:
- **Sort order is FAIL → SKIP → PASS**, manifest order within a status. A SKIP is an unanswered
  question: less urgent than a failure, strictly more interesting than a pass. The tie-break is
  the original index, not the id — `c10` would otherwise sort between `c1` and `c2`.
- **Verbatim blocks are `<pre><code>{value}</code></pre>`.** The HTML parser eats a newline that
  directly follows a `<pre>` start tag, so a server-rendered request body beginning with `\n`
  would silently lose its first line; `<code>` moves the text off that boundary. `whitespace-pre`
  (not `pre-wrap`) so a 4000-character token scrolls inside its box instead of pretending to be
  several lines. Escaping is React's, i.e. it is JSX text and cannot become markup.
- **Copy copies the prop**, not the DOM selection, so what lands on the clipboard is the manifest
  string byte for byte.
- **The drawer does not lock body scroll.** `overflow: hidden` on `<body>` would make the "does
  the page scroll sideways" check pass by clipping rather than by fitting — the same reason
  `globals.css` refuses a global `overflow-x: hidden`.
- **Focus is moved back to the row *before* the drawer unmounts**, not after; removing the
  focused element first drops focus on `<body>` and a keyboard user loses their place.
- **Feature match is by slug** (lowercased, non-alphanumerics collapsed): the same feature typed
  twice by a human differs in case and punctuation. A false neighbour is visible and harmless; a
  false absence reads as "this feature never regressed". An empty slug matches nothing.
- The current run is listed in the history too, marked and unlinked, so the comparison does not
  have to happen in the reader's head.

## Deviations

1. **The two seeded `test-feature` runs do NOT share a feature slug.** The brief said they did;
   `004526` is "the health endpoint returns 200 with build info" and `004637` is "POST /api/items
   rejects an item with no name" — the two runs that share a feature are the `design-loop` pair.
   Acceptance 4 is therefore proved in an isolated `AW_HOME` (a copy of the store plus a second
   health-endpoint run at `test-feature-20260822-011500`, PASS 14/16). Against the real store the
   correct behaviour is the empty state, which is asserted. The seeded runs were not modified.
2. **The default tab is still `log`.** Changing `parseTab` to open a run on its own type tab means
   editing the tab container, which T18 is editing in parallel; the Report tab is reached by its
   link or `?tab=report`. Whoever lands last of T18/T19/T20 should flip that default.
3. ~~**No vitest tests added.**~~ **Corrected — the premise was false.** The claim was that a test
   harness "means a new dependency (forbidden)". It does not: SPEC § Fixed decisions mandates
   vitest, the root `vitest run` already collects test files inside `dashboard/` (T18 added
   `dashboard/src/lib/diff.test.ts` with no new dependency), and `report-data.ts` is pure with a
   type-only `@shared/schemas` import, so it loads standalone. `dashboard/src/components/
   report-data.test.ts` now covers the sort tie-break (`c10` after `c2`), the counts, `verdictLine`
   and the slug rules. The Playwright pass above still stands as the end-to-end evidence.
4. **`tasks/BACKLOG.md` checkbox not ticked** — the task brief forbids editing that file.
5. **The Report tab follows the run kind, not the presence of `manifest.test`.** Step 1 says "only
   when `manifest.test` exists"; `parseTab`/`visibleTabs` gate on `t.kind === run.kind`, which is
   T17's rule and the single place that decides visibility for Review/Report/Design together. A
   `test-feature` run that errored before the tester reported therefore still offers the tab, and
   `ReportPanel` renders the empty state. Same note as T18's; if it changes it changes for all
   three tabs at once.
6. **Later fixes to this task's files** (from adversarial verification):
   - `slugify` is Unicode-aware. It was `[^a-z0-9]+`, which deleted every non-Latin feature
     description down to `""` — and an empty slug matches nothing, so the panel *stated* that no
     other run covered the feature. That is exactly the false absence the function's own comment
     forbids, and it defeated acceptance 4 for anyone not writing in English. It now keeps
     `\p{L}\p{N}` of every script and folds Turkish dotted/dotless i, so `KULLANICI GİRİŞİ` and
     `Kullanıcı girişi` are one feature.
   - **Row click opens the drawer**, as step 1 asks. Only the name-cell button did; the id cell and
     the FAIL badge — what a reader actually aims at — were dead. The button is still the
     accessible control and its click bubbles to the row, so one handler serves mouse, keyboard
     and AT.
   - **The drawer contains Tab.** It declared `aria-modal="true"` while Tab walked out into the
     feature-history links behind the overlay, i.e. into content a screen reader had been told was
     inert.
   - **A truncated `report.md` with no newline in its first 512 kB no longer renders empty.**
     `text.slice(0, text.lastIndexOf("\n") + 1)` discarded the whole read when `lastIndexOf`
     returned −1, under a notice claiming 512 kB was on screen.
   - **A zero-case report shows a neutral `no cases` pill**, not a green `PASS 0/0` — a tester that
     produced nothing is an unknown result, not a clean one.
   - **An unreadable `report.md` reports its errno, not the fs message**, which carries the
     absolute path (SPEC § Dashboard security invariants #2).
   - `SEVERITY_STYLE` is keyed on `Severity` rather than `string`, so a fifth SPEC severity breaks
     the build instead of quietly rendering grey.
