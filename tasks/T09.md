# T09 — `aw test-feature` workflow

Depends on: T08 (patterns), T06. Read first: `tasks/SPEC.md` (TestCase type, tools table).
Goal: black-box test run producing a report file.

## Steps

1. Create `src/workflows/test-feature.ts` exporting
   `runTestFeature(opts: { desc: string; url?: string; allowDestructive?: boolean; provider?: string; model?: string; config?: string; workspace?: string })`:
   1. Resolve config + model for agent `qa-tester` (same pattern as T08; same `claude-cli` refusal).
   2. Target = `opts.url ?? cfg.app?.baseUrl ?? 'http://localhost:' + cfg.app?.backend?.port`
      (none available → exit 1 `no target: pass --url or configure app.baseUrl`).
   3. Reachability: `fetch(target + (cfg.app?.backend?.healthPath ?? '/'))` with 5 s timeout.
      If down AND target is localhost AND `cfg.app?.backend?.start` exists: spawn it
      (`exec`, cwd `repoRoot`, detached, log to stderr), poll the same URL every 2 s for
      max 60 s. Still down → exit 1 with the command it tried.
   4. Safety: if target is NOT localhost — require that it equals `cfg.app.stagingUrl`
      (else exit 1: `non-local target must match app.stagingUrl`); pass
      `allowDestructive` through to `makeCoreTools`.
   5. Agent session (`generateText`, tools = tester profile + browser tools,
      `stopWhen: stepCountIs(40)`), prompt = feature/bug description + target URL + test
      account info (user + env var NAME only) + *"First write the test plan (happy, edge,
      invalid, auth). Then execute each case. Finally output a JSON block:"* followed by this
      exact required tail format:
      ```
      ===PLAN===
      <the test plan, as a short markdown list: happy / edge / invalid / auth>
      ===CASES===
      [ { TestCase }, ... ]
      ===SUMMARY===
      <3 lines max>
      ```
   6. Parse the tail (`===CASES===` JSON → `TestCase[].parse` via zod array; parse failure →
      one retry with format reminder, then exit 1 printing raw).
   7. Write report `test-reports/<slug(desc)>-<YYYY-MM-DD>.md` (in the TARGET repo root):
      title, target, provider/model, test plan, one section per case (status, kind,
      request/response verbatim for failures, repro steps, severity), summary. Create dir;
      never overwrite — append `-2`, `-3` to the filename if it exists.
   8. Print: report path + the 3-line summary + `PASS x/y`. Fix nothing.
2. `src/commands/test-feature.ts` → `registerTestFeature(program)`: arg `<desc>`, options
   `--url`, `--allow-destructive`, `--provider`, `--model`, `--config`, `--workspace`.
   Register in cli.ts.

## Acceptance

Against any running local endpoint (or one auto-started via config):
```
npx tsx src/cli.ts test-feature "health endpoint returns 200 with build info" --config <target>/aw.config.json
```
1. Prints a report path; the file exists and contains a test plan, ≥1 case with PASS/FAIL,
   and a summary.
2. A failing case (point it at a wrong port with `--url http://localhost:9`) still produces
   a report with the exact failed request recorded, exit 0 (test failures are findings, not
   CLI errors).

## Out of scope
No fixes to the target app. No manifest (T16).

## Deviations

1. **Auto-start only fires for the configured backend.** Step 3 says "down AND localhost AND
   `app.backend.start` exists → spawn it … still down → exit 1", but Acceptance 2 requires
   `--url http://localhost:9` to produce a report and exit 0. Taken literally the two
   contradict: port 9 is localhost and the fixture config has a `start` command, so the run
   would boot the API on 3001, keep polling port 9, and exit 1 after 60 s. Resolved by starting
   the app only when the target *is* the backend the config knows how to start (its port equals
   `app.backend.port`, or its origin equals `app.baseUrl`). Any other local target that is down
   is tested as given, and its refused connections become FAIL cases. Exit 1 with the attempted
   command therefore happens only after a start was actually attempted, which is also the only
   case where "the command it tried" exists to print.

2. **`ensureUp` uses `spawn(cmd, { shell: true, detached: true })`, not `exec`.** Same shell,
   same detached process group; `exec` additionally buffers the child's stdout and kills it when
   `maxBuffer` is exceeded, which for a dev server that logs every request means the app under
   test dies mid-run. `spawn` streams the output to stderr line by line instead.

3. **A missing `===SUMMARY===` is a warning, not a retry.** Step 6 makes only the `===CASES===`
   JSON a retry trigger. The cases are the result; when the marker is absent the summary falls
   back to `PASS x/y` and the omission is recorded in the report's parser notes.

4. **The format retry runs with no tools and replays its own tool log.** Re-sending the original
   prompt (the T08 pattern) made the local 30B model run a second full 40-step session — about
   seven minutes to produce nothing, twice. The retry now gets a single toolless turn containing
   the session's tool calls and results, and is told to report only what that log supports. Still
   exactly one retry, still exit 1 printing the raw text if it fails.

5. **The session also stops on a stuck agent:** `stopWhen` is
   `[stepCountIs(40), isLooping]`, where `isLooping` is five consecutive identical tool calls
   (observed: `git_log {"limit":5}` twenty times in a row until the step budget ran out).

6. **Three report sections beyond the list in step 7**, all about not overstating the result:
   an "Evidence is off target" banner when a case's request names an origin other than the
   target (observed: pointed at a dead port, the model started the app itself and graded eight
   cases against `:3001`), an "Unparseable cases" section reproducing case objects that failed
   validation instead of dropping them, and "Parser notes" listing every tolerated deviation.

### Architect amendment (2026-08-21)

Step 5's required tail now begins with a `===PLAN===` section. Reason: in the live acceptance
run the report's "Test plan" section was filled with the model's restart narration — the same
plan restated five times, interleaved with "Let me check…" lines — because the plan was
recovered from free narration. The plan must come back through the same structured tail as the
cases. Parsing rule: `===PLAN===` is a warning-not-retry omission (like `===SUMMARY===`); when
it is absent, fall back to narration but collapse repeated paragraphs and cap the section.
